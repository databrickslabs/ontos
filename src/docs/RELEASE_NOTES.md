# Release Notes - Unreleased


## ⚠️ Upgrade Notes

- **workflows**: rules on `tag_count`, `has_tags` and `HAS_TAG` / `TAG` now see the tags assigned to data products and data contracts. Before, the rule object of a product or contract counted assignments under `DataProduct` / `DataContract`, while tags are stored under `data_product` / `data_contract`, and it had no `tags` field: `tag_count` was always 0, `has_tags` always false and `HAS_TAG(...)` always false. This applies to workflow validation steps that read the stored product or contract (all triggers except `before_create`, `before_update` and `on_delete`) and to maturity gates. Results can change in both directions on upgrade: a rule that requires tags (`HAS_TAG('owner')`, `obj.tag_count > 0`) can now pass, so its `ON_FAIL` branch (for example an auto-assign tag step) stops running where the tag exists; a rule that requires no tags (`NOT HAS_TAG(...)`, `obj.tag_count = 0`, `obj.has_tags = false`) can now fail and fire its `ON_FAIL` branch; maturity levels with the "Tags assigned" gate can go up. What to check: in Settings > Workflows, review the active workflows on data products and contracts whose validation steps use these fields, and the maturity gates that use them.
- **workflows**: rules on `quality_check_count` and `has_quality_checks` now see the quality items of data products and data contracts. Before, the rule object looked them up under `DataProduct` / `DataContract`, while quality items are stored under `data_product` / `data_contract`, so the count was always 0 and `has_quality_checks` always false, in workflow validation steps that read the stored product or contract and in maturity gates. Results can change in both directions on upgrade, as for tags above: a rule that requires quality checks can now pass (and its `ON_FAIL` branch stops running), one that requires none can now fail, and maturity levels with the "Quality checks active" gate (`obj.quality_check_count > 0`) can go up. What to check: the active workflows and maturity gates that use these fields.
- **workflows**: stored workflows whose trigger lists an entity type that matches no event (a type that no longer exists, such as `dataset`, or a type the trigger never fires for, such as `before_update` on `data_product`) are kept as stored and not deactivated. At startup the backend logs one warning per such workflow (id, name, trigger type, entity types), and `GET /api/workflows` and `GET /api/workflows/{id}` list them in `trigger_warnings` (codes `stored_entity_type_unknown` and `stored_entity_type_unsupported`). What to check: the startup log, then pick a supported entity type for those workflows or delete them.
- **workflows**: `policy_check` steps now select entities as a compliance run does. A policy whose `MATCH` type is not the step's entity type, or whose `WHERE` doesn't select the entity, no longer applies: the step passes with `not_applicable` (and `reason: match_type` or `where`) in its result data, and the workflow follows `on_pass`. Before, only the `ASSERT` was evaluated, on the trigger payload and the stored product or contract, so such a step usually failed (for example a data contract policy on a data product workflow, or the retail "Contract Purpose Described" policy on draft contracts). A `WHERE` that can't be evaluated (for example a string compared with a number) fails the step with the error code `rule_where_evaluation_failed`, so it doesn't let a gate pass. On `before_update` gates the `WHERE` sees the stored contract with the proposed change over it, and the `ASSERT` still sees only the proposed change. `MATCH (r:review)` and `MATCH (r:data_asset_review)` both select review workflows. For data products, data contracts, domains and reviews, `WHERE` and `ASSERT` now see the entity as a compliance run does (`description` is the purpose text, `owner`, `tags` as `{name: value}`). What to check: in Settings > Workflows, the active workflows with policy checks, especially gates (`before_status_change`, `before_update`) whose policy's `MATCH` type differs from the trigger's entity types: they now pass where they used to fail.
- **compliance**: compliance runs see two corrected keys. A data product's `description` is now its purpose text (`None` when it has no description); before, it was the ODPS description row, so `LENGTH(p.description)` was an evaluation error and a rule on `p.description` could pass on an empty purpose. A review's `reviewer` and `requester` are now its reviewer and requester emails; before, they were always `None`. The review keys `asset_id` and `asset_type`, always `None`, are removed. Results can change in both directions on the next run: rules on a product's description that errored or passed on an empty purpose can now pass or fail on the purpose text, and rules on a review's `reviewer` / `requester` now see values. What to check: in Compliance, the policies that read a data product's `description` or a review's `reviewer`, `requester`, `asset_id` or `asset_type`.
- **compliance**: Unity Catalog views are now loaded as `view` entities (#1346). Before, the loader compared the SDK's table type with the string `VIEW`, which never matched, so every view, materialized view and metric view was a `table`. Existing `MATCH (t:table)` rules stop seeing views, and `MATCH (v:view)` rules start matching them; `MATCH (obj:Object)` with `obj.type IN ['table', 'view']` covers both. Materialized and metric views count as views, and `table_type` keeps the exact type. Tables and views also gain column fields for rules: `columns`, `column_count`, `columns_without_comment_count`, `column_comment_ratio` (null when there are no columns), `partition_column_count` and `partition_columns_without_comment_count`. What to check: in Compliance, review the policies that use `MATCH (t:table)` and are meant to cover views, and the results of policies on `MATCH (v:view)`, which may now report findings for the first time.
- **data-products**: the write routes now answer with the same keys as `GET /api/data-products/{id}`. This affects `POST /api/data-products`, `POST /api/data-products/from-contract`, `POST /api/data-products/{product_id}/versions`, `PUT /api/data-products/{product_id}` and `POST /api/data-products/{product_id}/clone-for-editing`. Before, their response body used the aliases of the data product model, which differ from the `GET` keys, so an API client had to read one key on write and another on read. The request bodies are unchanged. Keys that change in the response (old, then new): on the product, `api_version` to `apiVersion`, `authoritative_definitions` to `authoritativeDefinitions`, `custom_properties` to `customProperties`, `input_ports` to `inputPorts`, `output_ports` to `outputPorts`, `management_ports` to `managementPorts`, `support_channels` to `support`, `product_created_ts` to `productCreatedTs`, `draftOwnerId` to `draft_owner_id`, and the versioning keys `parentProductId`, `versionFamilyId`, `baseName`, `changeSummary` and `versionCount` to `parent_product_id`, `version_family_id`, `base_name`, `change_summary` and `version_count`. In each input port: `contract_id`, `contract_name`, `asset_type`, `asset_identifier` to `contractId`, `contractName`, `assetType`, `assetIdentifier`. In each output port: `port_type`, `contract_id`, `contract_name`, `input_contracts`, `delivery_method_id`, `asset_type`, `asset_identifier`, `contains_pii`, `auto_approve` to `type`, `contractId`, `contractName`, `inputContracts`, `deliveryMethodId`, `assetType`, `assetIdentifier`, `containsPii`, `autoApprove`; in each of its input contracts `contract_id` and `contract_version` to `id` and `version`; in each of its servers `schema` to `schema_name`. In each management port `port_type` to `type`; in each support channel `invitation_url` to `invitationUrl`; in each team member `date_in`, `date_out`, `replaced_by_username` to `dateIn`, `dateOut`, `replacedByUsername`. The UI only reads `id` from these responses and is not affected. What to check: scripts and integrations that read a product from the response of one of these routes (for example `output_ports` after `POST /api/data-products`) and update them to the `GET` keys, or read the product with `GET` after writing.

- **compliance**: the `NOTIFY` action now sends in-app notifications. Before, every `NOTIFY` in a policy run failed (no notification service was passed to the run), silently. Each recipient gets **one notification per run**: the run's failed and passed totals, up to 10 of the entities its NOTIFY actions ran for, and a link to the run results. It doesn't send one notification per entity. Recipients resolve as in workflow notification steps (emails, groups, roles, `entity_owner`; `owner` now means the entity's owners). Saving or running a policy with `NOTIFY` now needs admin access to compliance, because the action can notify any user, group or role. What to check: in Compliance, the active policies with `NOTIFY`, especially those run by the compliance-checks job. Their recipients start receiving notifications on the next run. Users with only write access to compliance can no longer change the rule of such a policy.
- **compliance**: `ASSIGN_TAG` and `REMOVE_TAG` accept a quoted fully qualified key (`ASSIGN_TAG 'governance/classification': 'confidential'`) and `ASSIGN_TAG` accepts a key without a value (`ASSIGN_TAG 'pii'`). A key-only assignment keeps the value an entity already has; `''` clears it. A value outside the tag's possible values now fails the action (*value not allowed*); before, any value was stored. Existing rules (`ASSIGN_TAG key: 'value'`) work unchanged. The run details page lists each entity's tag and notification actions and why one failed.
- **workflows**: **Reload All Defaults** keeps default workflows that a user edited, and never changes whether a workflow is active. Before, it reset every default to the shipped definition, including edits and the active flag, without asking. The page now asks first and offers an option to also reset edited defaults. New column `process_workflows.is_customized` (migration `s1_workflow_is_customized`); existing defaults last updated by a user (`updated_by` other than `system`) are marked customized, including ones that were only switched on or off. Tick the option once to bring those back to the shipped definition. Automation that calls `POST /api/workflows/load-defaults?update_existing=true` to reset defaults should add `include_edited=true` if it relied on overwriting edits.
- **workflows**: Pass and Fail steps now end a process workflow's run. Workflows built with designers before v1.1.0 can hold a link out of a Pass or Fail step that the canvas never drew; the executor followed it, so a run could go on from its Pass step into a Fail step and end as failed. That link is now ignored, reported by `POST /api/workflows/validate` as the warning `terminal_step_has_next`, and removed when the workflow is saved. Approval (wizard) workflows are unchanged. What to check: Recent Executions of workflows that ended on a Fail step right after a Pass step; they now end as succeeded.
- **workflows**: a conditional step whose condition could be evaluated now succeeds, true or false, and records `result` and `branch` (`"true"` / `"false"`). The result still picks `on_pass` (true) or `on_fail` (false), but a false condition is no longer counted as a failure, and a false condition with no step on `on_fail` ends the run as **succeeded** (before: failed). A condition that can't be evaluated fails the step and ends the run as failed; before, it followed `on_fail` like a false condition. `${step_results.<id>.passed}` of a conditional is now true whenever it was evaluated; use `${step_results.<id>.branch}`. Validation warns about a conditional without a step on one of its branches (`conditional_branch_missing`). What to check: gates (`before_*` triggers) with a conditional step that has no `on_fail`: they used to refuse the change when the condition was false and now let it through; add a Fail step on the false branch to keep refusing it.
- **workflows**: the Workflow Designer shows problems, not only errors. **Check** (next to Save) runs the validation without saving and lists its errors and warnings in a panel; a step a warning is about gets an amber ring, and clicking the entry selects it. Warnings don't block a save: `terminal_step_has_next`, `conditional_branch_missing` (a conditional with no step on a branch) and `unreachable_steps`. The stored trigger warnings (`stored_entity_type_unknown`, `stored_entity_type_unsupported`) show on the trigger node. The workflows list marks a workflow whose stored trigger has warnings. What to check: open the workflows with the badge, or Check the gates whose conditionals have no Fail step.
- **audit**: a data product deprecated or retired through Ask Ontos or MCP (`update_data_product` with a status) is now audited as `DEPRECATE` / `RETIRE`, as the `change-status` route does; `DEPRECATE` carries the deprecation reason, sunset date and replacement. Before, the tool always wrote `CHANGE_STATUS` with only the product id and the new status, so audit log filters or alerts on `DEPRECATE` / `RETIRE` missed those changes. Other transitions are still `CHANGE_STATUS`.
- **mcp**: the team, project, domain and tag tools (MCP and Ask Ontos) now apply the read rules of their REST routes to the caller. `search_teams` and `get_team` need Read-only on Teams, `search_domains` and `get_domain` Read-only on Data Domains, and `search_tags`, `get_tag` and `list_entity_tags` Read-only on Tags, as the matching `GET` routes; without it, the search tools return nothing and the get tools answer "not found". `search_projects` and `get_project` need Read-only on Projects and return only the projects `GET /api/projects` lists for the caller: everything for the admin groups, else the projects without an owning team or whose owning team has no domain, the projects assigned to one of the caller's teams, and those whose owning team shares a domain with one of the caller's teams. `global_search` drops the same projects and, as `/api/search`, returns nothing to a user with no groups. Before, these tools answered any token with the tool's scope. An MCP client that calls with an API key and no forwarded user token has no user, so it now gets no projects, as `GET /api/projects` without a user; its other reads still follow its token's scopes. What to check: MCP integrations that list projects with an API key only (forward the user's token, on-behalf-of, instead), and roles without Read-only on Teams, Projects, Data Domains or Tags whose users rely on these tools in Ask Ontos.
- **compliance**: the Compliance Checks job now receives the app's LLM settings (`LLM_ENABLED`, `LLM_ENDPOINT`, `COMPLIANCE_LLM_CHECK_MAX_CALLS_PER_RUN`) as job parameters, for the new `LLM_CHECK` rule function (#1479). A job installed before this release has no task arguments for them, so its scheduled runs fail every `LLM_CHECK` with `llm_check_disabled` until the job is rewritten. Saving the general settings (they include the LLM settings) redeploys such a job's code and rewrites its tasks and parameters once, keeping its schedule; reinstalling it works too. Rules without `LLM_CHECK` are not affected. What to check: if you use `LLM_CHECK` with the scheduled Compliance Checks job, save the general settings once after upgrading.
